# Explorer Rescue v0.2.11 完整接档说明

## 1. 项目目标

解决 Windows 11 File Explorer 偶发卡死后，传统重启 `explorer.exe` 会丢失全部已打开窗口和标签页现场的问题。

最高验收标准：

- 恢复原窗口数量；
- 保持每个窗口原有标签组合关系；
- 标签路径正确；
- 不把失败标签留成“此电脑/Home”并误判成功；
- 不额外残留 Shell 启动产生的默认 Explorer 窗口；
- 恢复原窗口位置/最大化状态；
- 位置不可信时在主显示器工作区中央恢复常规尺寸；
- 任务栏尽快恢复，不为会话恢复人为拖慢 Shell；
- 常驻 CPU、内存、线程、句柄、磁盘写入极低；
- 绿色、无注册表、无日志、无网络；
- 运行目录长期严格只有 `ExplorerRescue.exe / config.ini / sessions.dat`。

## 2. 当前实机稳定基线：v0.2.10

用户已实机确认 v0.2.10 “这次没问题了”。因此后续开发必须保护以下已验证主链：

- Windows 11 Explorer 按原窗口标签页组恢复；
- 标签实际路径恢复；
- 原窗口位置恢复；
- 位置不确定时主显示器工作区中央常规尺寸兜底；
- 任务栏快速恢复；
- 每个标签组的首窗口先完整加载/稳定，再创建后续标签；
- Shell 启动阶段产生的单标签“此电脑/Home”窗口可复用为第一组，避免额外残留；
- 全量恢复成功时才允许安全清理未使用 bootstrap，任何恢复失败都禁止破坏性清理；
- 托盘常驻与 `TaskbarCreated` 后重新注册；
- `Win + Shift + E` / 再次运行 EXE 执行 Explorer 重启恢复。

v0.2.11 **不修改 `explorer.cpp` 的上述稳定恢复主链**。

## 3. v0.2.11 本轮问题来源

长期使用 v0.2.10 后，用户确认恢复本身稳定，但后台经常出现扫描超时。

旧策略把以下概念错误地绑定在一起：

```text
某一轮 Shell COM 扫描失败/超时
= 扫描器已经不可信
= 永久停止后续扫描
```

这对长期常驻程序过于保守。Shell COM 偶发变慢可能来自：

- Explorer 正在切换/创建/销毁标签；
- Shell Extension 暂时卡顿；
- 网络/断开路径；
- 缩略图、快速访问或其他 Shell 内部工作；
- `Document.Folder.Self.Path` 跨进程 `IDispatch::Invoke` 暂时阻塞。

一次慢调用并不代表以后所有扫描都应该停止。

## 4. v0.2.11 新扫描事务模型

### 4.1 核心原则

每轮扫描独立：

```text
成功
→ 只有完整会话才允许进入 sessions.dat
→ 会话没变化则不重复写盘
→ 连续失败计数清零

失败
→ 当前轮直接丢弃
→ 最近 5 个有效历史完全不动
→ 下一周期自动再试
```

普通扫描失败不再设置 `g_scanPaused`。

### 4.2 连续失败通知

新增配置：

```ini
[Scan]
NotifyAfterConsecutiveFailures=3
```

默认逻辑：

```text
失败 #1 → 静默
失败 #2 → 静默
失败 #3 → 系统通知一次
失败 #4... → 不重复刷通知
任意一次成功 → 计数清零、允许下一轮新故障再次通知
```

旧 `config.ini` 没有该键时自动取默认值 3，不要求迁移文件。

### 4.3 watchdog 超时后的有界重试

不能简单在 watchdog 超时后把 `g_scanBusy` 清零并每 5 秒新建一个 COM 线程，因为真正卡住时会堆积永久挂起线程。

v0.2.11 采用双路径：

#### 正常路径

```text
后台定时器
→ 创建一个短命 COM 扫描线程
→ Shell.Application.Windows()
→ 完成后保存有效快照
→ 线程退出
```

#### 某个正常线程超过 watchdog

```text
当前 token 标记为 timed-out
→ 该线程结果从此永久作废
→ 不使用 TerminateThread
→ 让旧线程自行等待 COM 返回
```

只要该旧线程仍未返回，后续周期变成：

```text
ExplorerRescue.exe /capture-once
→ 独立子进程完成一次扫描
→ 成功则直接保存历史
→ 超时则父进程 TerminateProcess 子进程
→ 下一周期继续尝试
```

这样保证：

- 主守护最多只保留一个异常卡住的正常 COM 线程；
- 不会每 5 秒堆一个挂死线程；
- 子进程是一次性扫描，无长期状态，超时后整体结束比杀主进程内线程安全；
- 旧正常线程如果后来自己返回，其结果因为 token 已被标记废弃，绝不会写入历史；
- 旧线程返回后 `g_scanTimedOutToken` 自动清零，后续重新回到低开销正常线程扫描。

### 4.4 跨进程 sessions.dat 写入锁

隔离子进程会和主守护共享同一个 `sessions.dat`。为避免它恰好在 Explorer 重启/恢复阶段写入，v0.2.11 新增内核命名互斥量：

```text
Local\ExplorerRescue.SessionWrite.v1
```

所有 `SaveSnapshotHistory()` 调用都先取得该锁。Explorer 救援在真正结束 `explorer.exe` 前取得同一把锁，并持有到恢复结束。

因此：

- 隔离扫描与主线程不会同时改写 `sessions.dat`；
- Explorer 重启/恢复期间不会产生新的历史写入；
- 互斥量只存在于 Windows 内核对象命名空间，不创建文件、不写注册表；
- 所有进程关闭句柄后自动消失。

### 4.5 仍保留的保护性暂停

`g_scanPaused` 现在只代表：

> **Explorer 已经完成重启，但会话恢复结果本身失败。**

这时当前桌面可能是残缺恢复状态，如果立即周期扫描，很可能把残缺状态保存成新“有效历史”。所以这种情况继续暂停是合理的数据保护。

主动重启前的最终严格扫描失败则不同：

- 本次主动重启会取消；
- 不结束 Explorer；
- 但后台扫描不会永久暂停，会继续自动重试。

## 5. 扫描原语：保持 v0.2.10 不变

扫描事实来源继续严格参考用户 Mine_Exp 已实机工作的方式：

```text
Shell.Application.Windows()
→ w.Document.Folder.Self.Path
→ w.HWND
→ 相同 HWND 归入同一 Win11 标签组
```

不重新引入已经证明错误/过严的门槛：

- `CabinetWClass` 数量与 `Shell.Windows()` 硬一一对应；
- `FullName` 过滤；
- `Count` 前后必须一致；
- 两份完整二进制快照 hash 必须完全相同。

## 6. 托盘入口调整

用户长期使用后认为“重启并恢复资源管理器”放在托盘没有意义，因为 Explorer 救援本来已有更合适的入口：

- `Win + Shift + E`；
- 再次运行/从开始菜单启动 `ExplorerRescue.exe`。

因此 v0.2.11 托盘改为纯管理入口：

```text
重启 Explorer Rescue
立即扫描并保存会话
状态：...
退出 Explorer Rescue
```

双击托盘图标也改为“重启 Explorer Rescue”。

### 6.1 软件自重启实现

不能在旧守护还活着时直接运行第二个 EXE，因为项目现有语义规定：

```text
已有守护 + 再次运行 EXE = Explorer 救援
```

正确实现：

```text
托盘请求重启本软件
→ 设置 g_restartSelfRequested
→ 正常销毁隐藏窗口、托盘、热键、定时器
→ RunDaemon() 返回
→ CloseHandle(g_mutex)，释放单实例对象
→ 若隔离 /capture-once 正在运行，先等它完成或按 timeout 回收
→ CreateProcess 当前 ExplorerRescue.exe
→ 新进程作为全新守护正常启动
→ 旧进程退出
```

这样不会误触发 Explorer 重启恢复，也不会因为旧守护先退出而遗留孤儿扫描子进程。

## 7. sessions.dat

格式与 v0.2.10 完全不变：

- 单文件 5 槽历史；
- 每槽独立 Header/Hash/Payload Hash；
- 固定保留最近 5 个不同的有效会话；
- 完全相同会话不推进历史；
- 0 个 Explorer 窗口不推进历史；
- payload 当前为 v3，保存可靠 `screenRect`；
- 读取兼容旧 v2 历史。

失败扫描从不进入历史。

## 8. 窗口位置稳定规则

保持 v0.2.6 已实机确认逻辑：

捕获：

- `GetWindowPlacement()`：显示状态；
- `GetWindowRect()`：非最小化窗口真实屏幕坐标。

恢复：

- 普通/贴靠窗口：按 `screenRect`；
- 最大化：先定位目标显示器，再最大化；
- 最小化、无可靠坐标、旧 v2 历史：主显示器工作区中央常规尺寸；
- 标签恢复完成后再二次写回位置，防 Explorer 异步布局覆盖。

## 9. 标签恢复稳定规则

保持 v0.2.10：

```text
ShellTabWindowClass
新建标签：WM_COMMAND 0xA21B
关闭本次失败的新标签：WM_COMMAND 0xA021, lParam=1
```

新标签识别：

```text
创建前记录 (HWND, LocationURL)
→ 新建标签
→ 同 HWND ShellWindow 数量增加
→ 优先找新增 (HWND, LocationURL)
→ Navigate2(target)
→ 等待真实路径
```

整组最终校验只用于判断成功/失败；失败时不得关闭整个恢复窗口。

## 10. 首窗口与 bootstrap 稳定规则

每组首窗口必须：

- 顶层 HWND 可响应；
- `ShellTabWindowClass` 可响应；
- 同 HWND 当前只有首标签；
- 首标签路径正确；
- `Busy` 若可读取则为 false；
- 连续稳定至少 1200 ms。

第一组优先复用新 Shell 已产生的单标签 bootstrap frame；全量恢复成功后才允许清理未使用残留。该逻辑已在 v0.2.10 用户实机通过，本轮不改。

## 11. 已确认失败方案与踩坑

### 扫描

- `CabinetWClass` 数量硬对 `Shell.Windows()`：Win11 正常瞬态会误判；已删除。
- 强制两次完整序列化 hash 相同：过严；已删除。
- 自写 x64 `VARIANT` 16 字节：ABI 错；已修为 24 字节并 `static_assert`。
- **v0.2.10：一次后台扫描超时就永久停扫**：长期实机证明过于保守；v0.2.11 改为当前轮丢弃 + 自动重试。
- watchdog 超时后直接允许不断新建线程：会有线程堆积风险；v0.2.11 明确禁止，改用单个旧线程 + 子进程隔离重试。

### 恢复

- COM `IUnknown` identity 识别新标签：实机不可靠；已回到 `(HWND, LocationURL)`。
- 校验失败关闭整组重建：严重破坏性 bug；永久禁止。
- 只按首路径寻找新窗口：可能绑定错误 HWND；已改 before/new HWND。
- 首 HWND 刚出现就加标签：会抢跑破坏组；已加 1200 ms 首窗口稳定闸门。
- 无条件二次启动 `explorer.exe`：可能留下额外“此电脑/Home”；已加入 Shell 自动重拉宽限和 bootstrap 复用。
- v0.2.9 要求“全局唯一 Explorer HWND”才复用 bootstrap：实机仍残留；v0.2.10 改为按具体 HWND 判断并通过用户实机。

### 窗口位置

- 只用 `WINDOWPLACEMENT.rcNormalPosition`：不够可靠；现保存 `GetWindowRect` 屏幕坐标。
- 最小化时相信异常几何：会恢复成小窗；现位置不可靠时中央常规尺寸兜底。

### 装载

- 曾错误导入 `InterlockedCompareExchange` 导致 Loader 入口点错误；现使用 x64 编译器 intrinsic，导入表无该符号。

## 12. 绿色与资源约束

实际运行目录长期严格只有：

```text
ExplorerRescue.exe
config.ini
sessions.dat
```

不创建：

- 注册表项；
- 自启动；
- AppData 数据；
- 日志；
- 网络/遥测；
- 数据库；
- 额外辅助 EXE/DLL；
- 持久临时文件。

扫描隔离子进程仍然是当前同一个 `ExplorerRescue.exe /capture-once`，不是释放新文件。

常态仍采用轻量短命扫描线程；只有一次正常线程真正超时以后才临时使用进程隔离重试，因此不把“每 5 秒创建进程”变成正常路径。

## 13. 配置

首次生成默认：

```ini
[Scan]
IntervalSeconds=5
TimeoutMilliseconds=20000
NotifyAfterConsecutiveFailures=3

[Notification]
DurationSeconds=8
```

范围：

- `IntervalSeconds`：5~600；
- `TimeoutMilliseconds`：10000~120000；
- `NotifyAfterConsecutiveFailures`：1~60；
- `DurationSeconds`：3~30。

修改后重启 Explorer Rescue 生效。托盘现在已经提供“重启 Explorer Rescue”，适合应用配置变化。

## 16. 下一步实机验收

优先长期运行 v0.2.11，观察此前经常发生的扫描超时场景：

1. 单次/少量扫描失败不应永久停扫；
2. 默认连续 3 次才通知一次；
3. 通知必须明确“仍在自动重试，历史未覆盖”；
4. 后续成功后状态自动恢复；
5. 托盘“重启 Explorer Rescue”只重启本软件，不碰 `explorer.exe`；
6. 双击托盘行为同上；
7. `Win + Shift + E` 和再次运行 EXE 仍能按 v0.2.10 稳定主链重启/恢复 Explorer；
8. 标签组、窗口位置、bootstrap、任务栏速度均不得回归。
