# 万能乱码恢复 v0.2.0 完整接档说明

> 这是累计接档文档。只拿到本次压缩包即可了解目标、架构、原程序分析、成功与失败方案、验证情况、构建方法以及后续工作。当前交付为**源码与跨平台格式算法测试版**，不是已完成 Windows GUI 实机验收的 EXE 发行版。

## 一、项目目标与范围

将旧工具 `RenameFiles v1.3.4` 的可逆乱码恢复思想，重写为独立原生 Win32/C++17 文本修复工具。满足：

1. 编码逆转码不限日文：UTF-8、GBK/GB18030、Big5、Shift-JIS、CP949、西欧及其他常见代码页；自动候选、手动指定，支持最多两层编码错误。
2. 广域格式互转：UTF-8 URL 百分号（%XX）、表单百分号（+→空格）、HTML5 命名实体与数值实体、JavaScript/Unicode 转义、十进制/十六进制字节、Unicode 码点、Base64、Quoted-Printable。
3. **ASCII 互转**：`ABC ↔ 65 66 67`。中文等非 ASCII 字符按 UTF-8 字节列表表示，例如 `中文 ↔ 228 184 173 230 150 135`，不可误称中文是 ASCII。
4. 大段文字、整篇文章操作：无 260 字业务上限，使用动态内存；GUI/RichEdit 限制和物理内存仍可能形成约 2GB 级的实际边界。
5. 只接受**单个 TXT 文件**通过窗口拖入、拖到 EXE/快捷方式或文件选择对话框打开，打开后立即自动分析。直接粘贴到文本框的内容没有扩展名限制，可输入 ZIP 文件名、HTML 实体串等任意普通文字。
6. GUI 静态标签不使用传统灰底，文本和标签不能被挤掉；ICO 真实嵌入 EXE。编码、转义输出进入结果框，绝不直接修改原 TXT。
7. 交付完整、自包含的工程和中文文档；根目录严格为 `docs/`、`source/`、`release/`、`.build/`。代码、文档使用 UTF-8 无 BOM + CRLF。

## 二、原程序逆向分析：已经确认的事实

输入样本：`文字 文本 转码RenameFilesV1.3.4.exe`，SHA-256：

`f619deab551a60c033a43f674c451165433cd076a3b658c99fa9ce10bf706854`

- PE32/i386 原生 MFC42u 程序，时间戳为 2014-01-08，非 .NET。
- 导入 `MultiByteToWideChar`、`WideCharToMultiByte`，用 Windows 代码页做双向转换。
- `0x40188B`、`0x401AA9` 一带使用 CP932；`0x401B49` 使用 CP50221；`0x402278` 附近有明确 CP1252→UTF-8 恢复链。
- 相关路径使用 `0x104=260` 字符固定缓冲；资源中保留“文件名解码&批量重命名”“日文1/日文2”“转码文件内容(TXT文档)”等字样。
- 因而原理是 mojibake 逆转码，不是 OCR、翻译或日语语义识别。横向格式转义是后续自研实现，不能误称原程序已经具备。

`Main.cpp`：Windows GUI、DPI、RichEdit、打开/保存 TXT、单文件拖放、命令行文件入口、候选表、剪贴板、格式下拉框、编码/解码按钮。`WM_CTLCOLORSTATIC` 将静态标签绘制为透明背景并返回 `COLOR_WINDOW` 画刷。

`EncodingEngine.*`：Windows 代码页可逆恢复；先抽取长文本开头、中间和末尾进行候选搜索，再对选中路线转换全文；严格往返检查尽量避免 best-fit/默认字符损失。

`TransformEngine.*`：与 Windows API 无关的格式表示转换器。内部严格 UTF-8 编码解码、UTF-16 代理项处理、百分号分组解码、HTML 数值实体及 HTML5 命名实体、Unicode/JS 转义、十进制/十六进制 UTF-8 字节、Base64、Quoted-Printable、`U+XXXX` 码点。

`HtmlEntities.inc`：共 2125 条**以分号结束**的 HTML5 标准命名实体数据，覆盖组合字符。不接受无分号名称作为自动解码，避免普通文字如 `&copycat` 误判。

`config/AppIcon.ico`：16、20、24、32、40、48、64、128、256 像素。资源编译脚本实际引用 `../config/AppIcon.ico`，GUI 注册主窗口时使用 `IDI_APP_ICON`。

`tools/test_transform.cpp`：无需 GUI 的可重复自动化回归。`build.bat`：检查 MSVC、NMake 及 Windows SDK 的 `rc.exe` / `mt.exe`，必要时初始化 `vcvars64.bat`，通过 `subst` 将原项目目录映射到可用盘符以绕开非 ASCII 绝对路径，清除旧 `.build/msvc-x64` 缓存，在此目录构建、运行 CTest、成功后向 `release/万能乱码恢复.exe` 复制，并清理成功构建的中间文件。构建失败则保留 `.build` 供排查。正常成功或失败退出都会撤销当前构建创建的临时盘符映射。

## 四、算法原则与交互规则

### 4.1 两类不同问题

**垂直编码错配**：原字节曾被错误代码页解读，恢复链 `乱码 Unicode → 错读代码页重编码为字节 → 正确代码页解码为 Unicode`。用户可以选择两端代码页，也可以自动查看候选。

**横向表示形式**：原始文本并未因为代码页错配而丢失，只是被写成 `%E4%B8%AD`、`&#x4E2D;`、`\\u4E2D`、`228 184 173` 等表示，必须按格式解析，不能靠 CP932/GBK 候选评分处理。UTF-8 百分号串经过一层 URL 编码再包进 HTML 实体时，自动格式解码最多执行 3 轮。

### 4.2 自动分析策略

自动格式分析只主动检测具有明确语法的 `%HH`、以分号结束的 HTML 实体、`\\u`/`\\x`/`\\U` 转义。只找到有效变化才显示候选；这些格式候选在下拉框最前面，优先预览，而**输入文本始终不变**。普通数字、连续十六进制、Base64、Quoted-Printable 不自动猜测，避免误改随机正文。码页候选仍可在下拉框手动选取。低评分改善的代码页候选不会直接覆盖输出。

### 4.3 信息完整性边界

遇到已经变成 `?`、`�` 的数据，丢失的原始字节无法凭算法保证恢复。严格解析失败直接报错或保留百分号原文，不把错误默认替换成问号。Windows 文本框无法显示内部 NUL，GUI 主动拒绝展示这类结果。UTF-8 百分号解码在字节组不构成合法 UTF-8 时保留 `%XX` 原样；如原本是 GBK 字节，不能冒充已得到正确结果，应另行增加手动字节编码路径。

## 五、已经验证的成功方案

- Windows 代码页方案沿用 v0.1.1 源码：动态缓冲、Windows API、往返可逆校验与文本评分抽样。
- 正确复原实际混合格式文件名：`NPCSubtitles_v0.1e-log1_%E6%8C%89...zip` → `NPCSubtitles_v0.1e-log1_按需详细日志_已编译完整工程包_20261011.zip`。
- ASCII：`ABC` ↔ `65 66 67`，中文：`中文` ↔ `228 184 173 230 150 135`。
- 十六进制：`E4 B8 AD E6 96 87` 或 `E4B8ADE69687` → `中文`。
- HTML5：`&#x4E2D;` / `&amp;` / `&NotEqualTilde;`；JavaScript 代理项：`\\uD83D\\uDE00` → emoji。
- URL 与 HTML 实体嵌套：`%26%23x4E2D%3B` → `中`。
- 所有格式使用混合中英日韩俄阿拉伯文字与 emoji 的无损往返用例。
- 约百万字符级长文本分别执行 URL、HTML、数字字节往返用例，避免出现原程序固定长度截断。

上述格式测试已通过当前环境的 GCC C++17 实际编译/执行；**尚未在 Windows 实际构建和运行本次 GUI**。没有 Windows EXE 时 `release/` 为空，此状态是诚实保留，不用伪造 EXE。

## 六、已失败/已排除方案和设计风险

- **Hangul 额外加分**：某些中文走错误 CP949 二次恢复也会产生大量韩文，因此该加分会使错误候选靠前；现行编码引擎不使用该加分。
- **把 `%XX` 当成 HTML 文档解析**：用户的典型输入是 ZIP 文件名，复杂 DOM/脚本解析既不必要，也会损害文件名；因此当前只按文本格式解析。
- **对 Base64、全数字串一律自动尝试**：会把正常文本或随机标识误判为可转换内容，所以保留手动模式。
- **不合法 UTF-8 直接使用 U+FFFD**：会静默丢失数据；采用严格 UTF-8 校验，保留坏的百分号字节片段或明确报错。
- **承诺无限内存和无限文件大小**：单个 GUI 控件、Windows 转码 API 和实际 RAM 都存在极限，本项目只保证无 260 字/短句业务限制。
- **直接修改源 TXT**：自动检测有误判可能，故所有功能只预览到输出框，保存前由用户主动确认路径。

## 八、构建、发布和当前阻塞

Windows 安装 Visual Studio C++ 桌面开发工作负载、Windows SDK、CMake 后运行 `source/UniversalMojibakeRepair/build.bat`，必须看到 `[完成]` 和 CTest 通过后，使用 `release/万能乱码恢复.exe`。若构建失败则保留日志，不能将未经 Windows 编译的源文件描述成已交付的 Windows EXE。

**当前阻塞**：此执行环境没有 Windows SDK / MSVC / MinGW-w64 Windows 交叉工具链，无法直接完成 Win32 GUI 构建和实机验收。用户 Windows 实机三阶段构建记录依次为：首次 BAT 源码目录引号导致 CMake 参数串接；修复后 SDK 工具不可见；补全 SDK 路径后编译、资源编译均成功，但链接命令中的中文 PDB 绝对路径乱码并出现 `Unknown system error -1`。本版通过临时 ASCII 盘符隔离尝试处理最后一项，是否排除链接错误必须以后续实机构建为准。GUI 的 DPI、拖放、候选选择及 GBK/Big5/Shift-JIS 代码页恢复仍待 Windows 验证。

下一步：先在 Windows 构建、执行测试并验收；再根据真实反馈决定是否增加 `%XX` 指定 GBK/Big5 原始字节编码、URL-safe Base64、邮件 RFC2047、HTML 无分号实体等低优先级格式。新增范围须先明确与防误判策略。

### 中文路径编码导致链接失败的最新诊断

第二份用户实机日志显示：`cl.exe` 正常编译测试源；Windows Kits 10.0.26100.0 的 `rc.exe` 和 `mt.exe` 都已被 CMake 找到，`RC Pass 1` 成功；`LINK Pass 1` 中 `/pdb:` 指向的真实中文工程路径变成一串乱码，最终显示 `Unknown system error -1`。因此可以确认问题阶段已从“资源与清单工具不可见”转移到“链接调用失败”，**中文路径在工具链中的传递是首要嫌疑，并非已经完全证明的唯一原因**。

为避免让用户将完整源码工程重命名为英文目录，`build.bat` 在调用 CMake 前用系统 `subst` 分配未占用盘符，统一从映射目录读取英文命名的源码，并把所有中间文件存到同一项目的 `.build`。原始目录和数据没有移动，正常退出时清理映射，成功输出仍为原项目 `release/万能乱码恢复.exe`。构建环境不需要预先拥有固定盘符或管理员权限。若 Windows 返回新日志，首先核对 `/pdb:` 是否变成纯 ASCII 映射路径，再按实际错误继续处理。
