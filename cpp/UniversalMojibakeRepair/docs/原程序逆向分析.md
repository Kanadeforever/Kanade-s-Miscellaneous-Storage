# RenameFiles v1.3.4 原程序逆向分析

## 目标与样本

研究输入 EXE 中“为何部分日文乱码能够还原、为何不支持大段文字”的真实机制，作为独立重写算法的事实依据，不把旧程序二进制文件加入新工程。

样本文件：`文字 文本 转码RenameFilesV1.3.4.exe`

SHA-256：`f619deab551a60c033a43f674c451165433cd076a3b658c99fa9ce10bf706854`

## 已确认结构

原文件是 32 位 PE 原生程序，链接 MFC42u；PE 记录时间 2014-01-08。导入 `MultiByteToWideChar`、`WideCharToMultiByte`，使用 Windows 多字节代码页。窗口资源含“文件名解码&批量重命名 v1.3.4”“日文1”“日文2”等字符串及“转码文件内容(TXT文档)”入口。

明确代码线索：`0x40188B`、`0x401AA9` 的 CP932（Shift-JIS），`0x401B49` 的 CP50221（ISO-2022-JP），`0x402278` 附近 CP1252→UTF-8 恢复链，及 `0x4021F0` 一带的 `0x104`（260）字符短缓冲区。

## 工作机理

UTF-8 字节可能被误按 CP1252、CP932、GBK 等解释成 Unicode 字符，形成 mojibake。若错误解释仍然可逆，恢复方法是：用错误代码页把当前乱码编码回原字节，再按正确代码页解码。它不是翻译、字典纠正或 OCR。字节已经损坏/被替换或被删除时不能保证恢复。

旧软件的日文模式与短文本限制是代码页和短缓冲设计导致，不是文字恢复原理只适用于日语。

## 与新工程的界线

新工程是使用相同 Windows 标准 API 的独立实现。新工程的 `TransformEngine`（%XX、HTML5 实体、ASCII 字节数字、Unicode、Base64、Quoted-Printable）属于与原程序不同的“表示形式互转”能力，不能把这些算法误写为旧程序已有行为。GUI 完全重新构建，不依赖 MFC42u 或 260 字符固定缓冲。

## 尚未确认的部分

未证明原始 EXE 可以直接处理现代 HTML5 实体、Base64 或任意 Unicode 字节序列；不把推测列为确认事实。旧程序中历史组件对核心乱码恢复是否还有其它特殊逻辑未完全逐指令逆向；当前工程不依赖这些行为。
